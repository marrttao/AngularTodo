## Этап 1. Solution, 4 проекта, docker-compose

### Что сделано
- Solution `server/TodoApp.sln` и 4 проекта:
  - `TodoApp.Api` (шаблон `webapi --use-controllers`): контроллеры, `Program.cs`, конфиг;
  - `TodoApp.Services`, `TodoApp.Interfaces`, `TodoApp.DataAccess` (шаблон `classlib`).
- Ссылки между проектами (`ProjectReference` в `.csproj`):
  - `Services → Interfaces`
  - `DataAccess → Interfaces`
  - `Api → Services, DataAccess, Interfaces`
- `docker-compose.yml` поднимает MS SQL Server 2022 в контейнере.
- `.gitignore` исключает `bin/`, `obj/`, `node_modules/`; `.gitattributes` нормализует окончания строк между Windows и Linux.

### Ключевые концепции

**Solution и проект.** Проект (`.csproj`) — одна сборка (`.dll`). Solution (`.sln`) группирует проекты для IDE и `dotnet build`. Почему 4 проекта, а не 4 папки: ссылки между проектами проверяет **компилятор**. Если `Services` попробует использовать класс из `DataAccess`, код не соберётся. Границу между папками легко нарушить случайно.

**4-уровневая архитектура:**
| Уровень | Что делает | Аналогия |
|---|---|---|
| Controllers (`Api`) | принимает HTTP-запрос, вызывает сервис, возвращает HTTP-ответ | официант |
| Services | бизнес-логика: правила, проверки, «можно ли это сделать» | повар |
| Interfaces | контракты: «что умеет» каждый слой, без реализации | меню / договор |
| Data Access | работа с БД через EF Core | кладовая |

**Почему сущности лежат в `Interfaces`.** Интерфейс репозитория возвращает сущность (`Task<TodoItem?> GetByIdAsync(...)`). Если бы сущности лежали в `DataAccess`, то `Interfaces` ссылался бы на `DataAccess` (чтобы получить сущности), а `DataAccess` на `Interfaces` (чтобы реализовать интерфейс). Получился бы **цикл**, а .NET запрещает циклические ссылки между проектами.

**Dependency Inversion Principle (D в SOLID).** Модули верхнего уровня (Services) не зависят от модулей нижнего уровня (DataAccess). Оба зависят от **абстракций** (интерфейсов). Плюсы:
- `Services` не знает про EF Core/SQL, поэтому БД можно заменить, не трогая бизнес-логику;
- в unit-тестах вместо настоящего репозитория подставляется мок.

**Composition root.** Это единственное место, где «собираются» конкретные реализации, то есть `Program.cs` в `Api`. Поэтому `Api` ссылается на `DataAccess`: там мы говорим DI-контейнеру «когда просят `ITaskRepository`, создай `TaskRepository`».

**Docker / docker-compose.**
- *Образ (image)* — шаблон. *Контейнер* — запущенный экземпляр образа.
- `docker compose up -d` поднимает БД одной командой, без установки SQL Server на машину. У всех разработчиков одна и та же версия.
- `ports: "1433:1433"` — порт хоста : порт контейнера.
- `volumes` — данные БД хранятся вне контейнера и переживают `docker compose down`. Команда `down -v` удаляет и их.
- `healthcheck` — Docker периодически выполняет `SELECT 1`, чтобы понять, что БД готова.
- Пароль в compose-файле допустим **только для локальной разработки**.

### Вопросы и ответы

**1. Почему бэкенд разделён на 4 проекта, а не на 4 папки?**
> *Твой ответ:* «Чтобы при изменении одной части остальные не полетели за ней». Это верная мысль (слабая связанность), но не хватает главного аргумента.
>
> **Полный ответ:** во-первых, слои слабо связаны. Изменения в одном слое (например, замена EF Core на Dapper в DataAccess) не требуют менять другие, потому что они общаются через интерфейсы. Во-вторых, и это главное отличие от папок: **компилятор не даст нарушить архитектуру**. У `Services` просто нет ссылки на `DataAccess`, поэтому написать там `new AppDbContext()` невозможно. Папки такой защиты не дают.

**2. В какую сторону направлены зависимости? Почему `Services` не ссылается на `DataAccess`?**
> *Твой ответ:* «Для безопасности». **Неверно**, к безопасности это не относится.
>
> **Правильный ответ:** все зависимости направлены **к `Interfaces`** (центр, ни от кого не зависит). `Services` работает только с интерфейсами репозиториев и не знает, что внутри EF Core и SQL Server. Это **Dependency Inversion Principle**: бизнес-логика не зависит от деталей хранения данных. Польза: можно заменить БД, можно тестировать сервисы с моками. Сущности лежат в `Interfaces`, потому что иначе получилась бы циклическая ссылка `Interfaces ↔ DataAccess`.

**3. Зачем `Api` ссылается на `DataAccess`, если контроллеры не работают с БД напрямую?**
> *Твой ответ:* «Они ссылаются на запрос???» **Неверно.**
>
> **Правильный ответ:** только для **регистрации зависимостей в DI** (composition root). В `Program.cs` мы пишем `AddDbContext<AppDbContext>(...)` и `AddScoped<ITaskRepository, TaskRepository>()`, а для этого нужно видеть классы `AppDbContext` и `TaskRepository`. Контроллеры при этом используют только `ITaskService` и о репозиториях не знают.

## Этап 2. Сущности, DbContext, связи, миграция

### Что сделано
- Сущности `User`, `Category`, `TodoItem` (в `TodoApp.Interfaces/Entities`).
- `AppDbContext` с тремя `DbSet` и конфигурациями через **Fluent API** (`DataAccess/Configurations`).
- Миграция `InitialCreate`, `dotnet-ef` установлен как **локальный инструмент** (`dotnet-tools.json`, восстанавливается командой `dotnet tool restore`).
- Строка подключения в `appsettings.Development.json`.

### Модель данных
```
Users (Id, Email UNIQUE, PasswordHash, CreatedAt)
  │1
  ├──────────────* Categories (Id, Name, UserId)      UNIQUE (UserId, Name)
  │                    │1
  │                    │ (ON DELETE: NO ACTION в БД, EF ставит NULL)
  │1                   │*
  └──────────────* Tasks (Id, Title, Description, IsCompleted, DueDate, CreatedAt, CategoryId NULL, UserId)
```

### Ключевые концепции

**EF Core** — ORM: работаешь с C#-объектами, EF генерирует SQL. `DbContext` — сессия работы с БД (единица работы плюс трекинг изменений). `DbSet<T>` — таблица.

**Навигационные свойства** (`task.Category`, `user.Tasks`) — ссылки между объектами. **Внешний ключ** (`CategoryId`) — колонка в БД.

**Fluent API vs атрибуты.** Можно писать `[MaxLength(200)]` прямо в сущности, но мы держим сущности «чистыми» (без знаний о БД), а всю настройку схемы делаем в `IEntityTypeConfiguration<T>`. `ApplyConfigurationsFromAssembly` находит все такие классы автоматически.

**Миграции** — версионирование схемы БД кодом. `migrations add` сравнивает модель со снапшотом и генерирует C#-класс с `Up()`/`Down()`. `database update` применяет миграции. В Development API применяет их сам при старте (`Database.Migrate()` в `Program.cs`).

**Почему `TodoItem`, а не `Task`.** Имя `Task` конфликтует с `System.Threading.Tasks.Task`, а он используется в каждом async-методе.

**`DateOnly` для DueDate.** Срок — это календарный день без времени, поэтому нет проблем с часовыми поясами. В SQL Server хранится как `date`. `CreatedAt` — момент времени, его храним в **UTC**.

**Подвох: multiple cascade paths.** Хотелось `ON DELETE SET NULL` для `Categories → Tasks`. Но у задачи уже есть каскад от `Users`, и SQL Server запрещает два каскадных пути к одной таблице (`Users → Tasks` и `Users → Categories → Tasks`). Решение: `DeleteBehavior.ClientSetNull`. В БД стоит `NO ACTION`, а EF Core сам ставит `CategoryId = null` у **загруженных** задач. Поэтому `CategoryRepository.DeleteAsync` сначала загружает задачи категории (`LoadAsync`), потом удаляет категорию. Всё сохраняется одним `SaveChanges`, то есть в одной транзакции.

**Индексы.** `Email` уникальный (два пользователя с одним email невозможны даже при гонке запросов). `(UserId, Name)` у категорий уникальный. `(UserId, IsCompleted)` у задач ускоряет основной запрос.

**Value converter для `CreatedAt`.** SQL Server `datetime2` не хранит «вид» даты (UTC/local), и EF читает её как `Unspecified`, поэтому в JSON нет `Z`. Конвертер помечает прочитанное значение как UTC.

### Вопросы и ответы

**1. Что такое миграция и зачем она нужна?**
> Миграция — C#-класс, описывающий изменение схемы БД (создать таблицу, добавить колонку). Миграции хранятся в git вместе с кодом, поэтому схема БД версионируется так же, как код, и любой разработчик или сервер получает одинаковую БД командой `dotnet ef database update`. Таблица `__EFMigrationsHistory` хранит, какие миграции уже применены.

**2. Что произойдёт с задачами при удалении категории и почему не каскадное удаление?**
> Задачи остаются, у них `CategoryId` становится `null` (как в MS To-Do, где удаление списка не должно молча уничтожать данные пользователя). `SET NULL` на уровне БД SQL Server не разрешает из-за multiple cascade paths, поэтому используем `ClientSetNull`: EF Core сам обнуляет FK у загруженных задач перед удалением, в одной транзакции.

**3. Что такое трекинг изменений (change tracking) и `AsNoTracking`?**
> DbContext запоминает загруженные сущности и их исходные значения. При `SaveChanges` он сравнивает текущие значения с исходными и генерирует `UPDATE` только для изменённых полей. Поэтому в `UpdateAsync` достаточно вызвать `SaveChangesAsync()`. `AsNoTracking()` отключает трекинг для запросов только на чтение (списки), так быстрее и меньше памяти.

## Этап 3. Репозитории, сервисы, DI

### Что сделано
- Интерфейсы репозиториев (`IUserRepository`, `ICategoryRepository`, `ITaskRepository`) и сервисов (`IAuthService`, `ITokenService`, `ICategoryService`, `ITaskService`) лежат в `Interfaces`.
- Реализации репозиториев лежат в `DataAccess`, реализации сервисов в `Services`.
- Ручной маппинг entity → DTO (`Services/Mapping/MappingExtensions.cs`).
- Кастомные исключения: `NotFoundException`, `BadRequestException`, `ConflictException`, `UnauthorizedException`.
- Регистрация всего в DI (`Program.cs`, `AddScoped`).

### Ключевые концепции

**Repository** — прячет детали доступа к данным за интерфейсом. Сервис говорит «дай задачу 5 пользователя 3», а не пишет LINQ к `DbContext`.
**Важно:** каждый метод репозитория принимает `userId` и фильтрует по нему, поэтому получить чужие данные невозможно в принципе.

**Service** — бизнес-правила:
- `CategoryService`: имя уникально в пределах пользователя, иначе `ConflictException` (409);
- `TaskService`: категория задачи должна принадлежать тому же пользователю, иначе `BadRequestException` (400); задача не найдена → `NotFoundException` (404);
- нормализация: `Trim()`, пустое описание → `null`, `CreatedAt = DateTime.UtcNow`.

**Почему исключения, а не коды возврата.** Сервис не знает про HTTP. Он бросает доменное исключение («не найдено»), а middleware превращает его в HTTP-код. Сервисы и контроллеры получаются чистыми, без `if (result == null) return NotFound()`.

**Dependency Injection.** Класс не создаёт зависимости сам (`new TaskRepository()`), а получает их через конструктор. Контейнер видит, что `TaskService` нужен `ITaskRepository`, и смотрит, что для него зарегистрировано: `TaskRepository`. `TaskRepository` нужен `AppDbContext`, контейнер создаёт и его. Получается целое дерево объектов.

**Время жизни (lifetimes):**
| | Когда создаётся | Пример |
|---|---|---|
| `Transient` | при каждом запросе зависимости | лёгкие stateless-утилиты |
| `Scoped` | один раз на HTTP-запрос | `DbContext`, репозитории, сервисы |
| `Singleton` | один раз на всё приложение | кеш, конфигурация |

`DbContext` — Scoped (он не потокобезопасен, и на запрос нужен один экземпляр), поэтому всё, что от него зависит, тоже Scoped. **Нельзя** внедрять Scoped в Singleton (captive dependency).

**Ручной маппинг вместо AutoMapper** — 10 строк, явно видно, какие поля уходят клиенту, легко отлаживать.

**`IOptions<JwtOptions>`** — секция `"Jwt"` из `appsettings.json`, привязанная к классу (строгая типизация вместо `configuration["Jwt:Key"]`).

### Вопросы и ответы

**1. Зачем нужен слой репозиториев, если DbContext уже сам по себе repository + unit of work?**
> Честный ответ: для маленьких проектов это спорно, многие используют DbContext прямо в сервисах. Здесь репозиторий нужен потому, что (1) этого требует 4-уровневая архитектура задания; (2) сервисы не зависят от EF Core и тестируются с моками; (3) запросы к БД (фильтрация по `userId`, `Include`, пагинация) собраны в одном месте и не размазаны по сервисам.

**2. Чем отличаются AddScoped, AddTransient, AddSingleton? Почему у вас Scoped?**
> Transient — новый объект при каждом внедрении. Scoped — один на HTTP-запрос. Singleton — один на всё приложение. У нас Scoped, потому что `DbContext` должен жить в пределах одного запроса (он не потокобезопасен и копит трекинг изменений). Репозитории и сервисы зависят от него, поэтому у них то же время жизни.

**3. Как гарантируется, что пользователь не увидит чужие задачи?**
> `userId` берётся только из проверенного JWT (никогда из тела запроса или URL) и передаётся в каждый метод сервиса и репозитория. Все запросы к БД содержат `WHERE UserId = @userId`. Чужая задача просто «не найдена», и API отвечает 404.

## Этап 4. Контроллеры, DTO, валидация, обработка ошибок, Swagger

### Что сделано
- `AuthController`, `CategoriesController`, `TasksController`.
- Контроллеры принимают и возвращают **только DTO**.
- Валидация через **DataAnnotations** (`[Required]`, `[MaxLength]`, `[EmailAddress]`, `[Range]`).
- `ExceptionHandlingMiddleware` — глобальная обработка ошибок в формате **ProblemDetails**.
- Swagger UI с кнопкой **Authorize** для JWT.
- CORS для Angular (`http://localhost:4200`).

### Ключевые концепции

**DTO (Data Transfer Object)** — класс специально для API. Почему не отдавать сущности:
- **безопасность:** у `User` есть `PasswordHash`, а у сущности задачи есть `UserId`. Клиент не должен их видеть или менять (иначе возможен *over-posting*: прислать `"userId": 2` в теле);
- **циклы:** `Task.Category.Tasks[0].Category...` ломает JSON-сериализацию;
- **стабильный контракт:** можно менять БД, не ломая клиентов.

**`[ApiController]`** даёт:
- автоматическую валидацию: если `ModelState` невалиден, сразу возвращается **400** с `ValidationProblemDetails` (`{ errors: { Title: ["..."] } }`), и код метода даже не вызывается;
- автоматический биндинг тела запроса (`[FromBody]` не нужен для сложных типов).

**HTTP-коды в проекте:**
| Код | Когда |
|---|---|
| 200 OK | GET, PUT, login/register |
| 201 Created | POST (+ заголовок `Location` через `CreatedAtAction`) |
| 204 No Content | DELETE |
| 400 Bad Request | невалидные данные / несуществующая категория |
| 401 Unauthorized | нет токена, токен невалиден, неверный пароль |
| 404 Not Found | ресурса нет или он чужой |
| 409 Conflict | email или имя категории уже заняты |
| 500 | непредвиденная ошибка (детали только в логах) |

**Middleware и pipeline.** Запрос проходит через цепочку middleware по порядку, ответ идёт обратно в обратном порядке (как матрёшка). `ExceptionHandlingMiddleware` стоит **первым**, оборачивает всё в `try/catch` и превращает исключения в JSON-ответ. Для 500 мы логируем детали, но клиенту не отдаём (stack trace — это утечка информации).

**Порядок middleware важен:** `ExceptionHandling → CORS → Authentication → Authorization → Controllers`. Аутентификация («кто ты?») должна идти раньше авторизации («можно ли тебе?»).

**CORS.** Браузер блокирует запросы JS с одного origin (`localhost:4200`) на другой (`localhost:5000`), если сервер явно не разрешил этот origin. Перед «сложными» запросами (с заголовком `Authorization` или JSON) браузер шлёт **preflight** `OPTIONS`. CORS — защита **браузера**, Postman и curl её игнорируют.

**Swagger / OpenAPI** — автоматически сгенерированная документация API и UI для ручного тестирования. `AddSecurityDefinition` + `AddSecurityRequirement` добавляют кнопку Authorize.

### Вопросы и ответы

**1. Почему контроллеры не возвращают сущности EF напрямую?**
> Безопасность (утечка `PasswordHash`, over-posting `UserId`), циклические ссылки навигационных свойств ломают сериализацию, и API-контракт не должен зависеть от структуры БД. DTO показывают ровно то, что нужно клиенту.

**2. Как работает глобальная обработка ошибок? Почему не try/catch в каждом контроллере?**
> `ExceptionHandlingMiddleware` стоит первым в pipeline и оборачивает вызов следующих middleware в `try/catch`. Сервис бросает, например, `NotFoundException`, middleware ловит его и по типу выбирает HTTP-код (`switch` по типу исключения), а ответ отдаёт в стандартном формате ProblemDetails. Плюсы: нет дублирования, единый формат ошибок, контроллеры остаются тонкими.

**3. Чем 401 отличается от 403? А почему для чужой задачи вы возвращаете 404?**
> 401 — «я не знаю, кто ты» (нет или невалиден токен). 403 — «я знаю, кто ты, но тебе нельзя». Для чужой задачи мы возвращаем 404, а не 403, чтобы не раскрывать сам факт существования задачи с таким id (иначе можно перебором узнавать чужие id).

## Этап 5. Аутентификация: JWT, BCrypt, [Authorize]

### Что сделано
- Регистрация и логин (`AuthService`), хеширование пароля **BCrypt**.
- Генерация JWT (`TokenService`), валидация JWT (`AddJwtBearer` в `Program.cs`).
- `[Authorize]` на `TasksController` и `CategoriesController`.
- `User.GetUserId()` читает id пользователя из claim `sub`.

### Ключевые концепции

**Аутентификация vs авторизация.** Аутентификация — *кто ты* (логин, проверка токена). Авторизация — *что тебе можно* (`[Authorize]`, доступ только к своим задачам).

**Хранение паролей.** Пароль **никогда** не хранится в открытом виде. BCrypt:
- **соль:** случайная строка добавляется к паролю перед хешированием. Одинаковые пароли дают разные хеши, и rainbow tables бесполезны. Соль хранится внутри строки хеша (`$2a$11$<соль><хеш>`);
- **медленный намеренно** (work factor): перебор миллиардов паролей становится очень дорогим. Обычный SHA256 для паролей не годится, потому что он слишком быстрый;
- проверка: `BCrypt.Verify(введённый, хеш)` берёт соль из хеша, хеширует введённый пароль и сравнивает.

**JWT (JSON Web Token)** = `header.payload.signature` (три части в Base64Url):
- **header:** алгоритм (`HS256`);
- **payload:** claims: `sub` (id пользователя), `email`, `exp` (срок), `iss` (кто выдал), `aud` (для кого);
- **signature:** HMAC-SHA256 от header+payload с **секретным ключом** сервера.

Payload **не зашифрован**, его может прочитать кто угодно (jwt.io), поэтому секреты туда не кладут. Но **подделать нельзя**: при изменении payload подпись перестанет сходиться, а ключа у клиента нет.

**Как проходит запрос с токеном:**
1. Логин → сервер проверяет пароль → выдаёт JWT.
2. Клиент хранит токен и шлёт заголовок `Authorization: Bearer <token>` с каждым запросом.
3. Middleware `UseAuthentication` проверяет подпись, `iss`, `aud`, `exp` и заполняет `HttpContext.User` claims из токена.
4. `[Authorize]`: если пользователь не аутентифицирован → 401.
5. Контроллер берёт `userId` из claim `sub`.

**JWT stateless — что это значит.** Сервер **не хранит** сессии. Вся информация уже в токене, и сервер только проверяет подпись. Плюсы: не нужно хранилище сессий, легко масштабировать на несколько серверов. **Минусы:**
- **нельзя отозвать токен** до истечения срока: logout на клиенте просто удаляет токен, но если его украли, он валиден до `exp`;
- смена пароля или блокировка пользователя не «выкидывает» уже выданные токены;
- поэтому токен делают короткоживущим (у нас 60 минут). В проде добавляют **refresh token** (долгоживущий, хранится в БД, можно отозвать) и/или чёрный список токенов.

**Одинаковое сообщение** «Invalid email or password» для «нет пользователя» и «неверный пароль» не даёт узнать, какие email зарегистрированы (user enumeration).

**`MapInboundClaims = false`.** По умолчанию ASP.NET переименовывает `sub` в длинный `http://schemas.xmlsoap.org/.../nameidentifier`. Мы отключили это, чтобы claim назывался так же, как в токене.

**`ClockSkew = TimeSpan.Zero`.** По умолчанию токен принимается ещё 5 минут после `exp` (запас на рассинхрон часов). Мы убрали этот запас, чтобы срок действия был точным.

### Вопросы и ответы

**1. Как работает JWT и почему его нельзя подделать?**
> JWT состоит из header, payload и signature. Подпись — это HMAC-SHA256 от header+payload, посчитанный секретным ключом, который есть только у сервера. При каждом запросе сервер пересчитывает подпись и сравнивает её с пришедшей. Если кто-то изменил payload (например, `sub`), подпись не совпадёт, и сервер вернёт 401. Прочитать payload может кто угодно, поэтому секретов там нет.

**2. Как реализован logout и какие минусы у stateless JWT?**
> Logout на клиенте удаляет токен из localStorage. Серверу ничего не сообщаем, потому что он сессий не хранит. Минус: токен нельзя отозвать до истечения срока. Если его украли, он работает до `exp`. Решения: короткий срок жизни + refresh tokens, хранимые в БД (их можно отозвать), или blacklist отозванных токенов (но тогда теряется часть «stateless»).

**3. Почему пароли хешируются BCrypt, а не SHA256? Что такое соль?**
> Соль — случайные данные, добавляемые к паролю перед хешированием, уникальные для каждого пользователя. Одинаковые пароли дают разные хеши, а заранее посчитанные таблицы (rainbow tables) не работают. SHA256 очень быстрый, и GPU перебирает миллиарды вариантов в секунду. BCrypt намеренно медленный (настраиваемый work factor), поэтому перебор становится непрактичным.

## Этап 6. Пагинация, поиск, фильтрация

### Что сделано
`GET /api/tasks?page=2&pageSize=10&search=milk&categoryId=3&isCompleted=false`
→ `{ items, totalCount, page, pageSize, totalPages }`

### Ключевые концепции

**`[FromQuery] TaskQueryParameters`** — query-параметры собираются в один объект с валидацией (`page >= 1`, `1 <= pageSize <= 50`). Ограничение `pageSize` защищает от `pageSize=1000000`.

**IQueryable и отложенное выполнение.** В `TaskRepository.GetPagedAsync` мы шаг за шагом добавляем `.Where(...)` к `IQueryable`, но **запрос в БД не уходит**, пока не вызовем `CountAsync()`/`ToListAsync()`. EF Core собирает всё в **один SQL-запрос** и фильтрует на стороне БД. Если сделать `ToList()` в начале, вся таблица загрузится в память.

**Два запроса:**
1. `SELECT COUNT(*) ... WHERE <фильтры>` даёт `totalCount`;
2. `SELECT ... WHERE <фильтры> ORDER BY ... OFFSET (page-1)*size ROWS FETCH NEXT size ROWS ONLY` даёт одну страницу.

`totalPages = ceil(totalCount / pageSize)`, например 21 / 10 → 3.

**Стабильная сортировка обязательна для пагинации.** Без `ORDER BY` SQL не гарантирует порядок, и одна задача может попасть на две страницы. У нас порядок такой: активные сначала, потом новые, а `Id` идёт последним как tie-breaker.

**Поиск:** `Title.Contains(search)` транслируется в `LIKE '%search%'`. Регистр игнорируется благодаря collation SQL Server по умолчанию (`..._CI_AS`, CI = case insensitive). Параметры передаются как SQL-параметры, поэтому SQL-инъекция невозможна.

**Offset vs cursor (keyset) пагинация.** Offset прост и позволяет перейти на любую страницу, но на больших таблицах `OFFSET 100000` медленный, и при добавлении записей возможны «сдвиги». Cursor-пагинация (`WHERE Id < lastId`) быстрая, но позволяет только «дальше/назад».

### Вопросы и ответы

**1. Почему пагинация и фильтрация сделаны на сервере, а не на клиенте?**
> На клиенте пришлось бы загружать все задачи пользователя: при тысячах записей это медленно, много трафика и памяти. На сервере БД отдаёт только нужные 10 строк, а фильтрует по индексам. Клиент получает `totalCount`/`totalPages`, чтобы нарисовать пагинатор.

**2. Что такое IQueryable и когда запрос реально уходит в БД?**
> `IQueryable` — описание запроса (дерево выражений), а не данные. Каждый `.Where()` дополняет описание. Запрос выполняется только при материализации: `ToListAsync`, `CountAsync`, `FirstOrDefaultAsync`, `foreach`. EF Core транслирует всю цепочку в один SQL-запрос.

**3. Зачем `OrderBy` при пагинации?**
> Без явной сортировки SQL Server может возвращать строки в любом порядке, и между запросами страниц порядок может отличаться. Тогда одни записи дублируются на разных страницах, а другие пропадают. Нужна детерминированная сортировка с уникальным tie-breaker (`Id`).

### Вопросы и ответы

**1. Что такое standalone component и чем он отличается от компонента в NgModule?**
> Standalone component сам объявляет свои зависимости в `imports` и не требует NgModule. Это проще (меньше boilerplate), каждый компонент самодостаточен, удобнее lazy loading. С Angular 19 это поведение по умолчанию.

**2. Что такое signal и чем он отличается от обычного поля класса?**
> Signal — реактивная обёртка над значением: `count()` читает, `count.set()`/`update()` пишет. Angular знает, какие шаблоны и `computed` читают сигнал, и при его изменении обновляет только их. Изменение обычного поля в zoneless-приложении Angular может «не заметить».

**3. Как работает DI в Angular и что значит `providedIn: 'root'`?**
> Класс помечается `@Injectable`, а зависимости получаются через `inject(SomeService)`. `providedIn: 'root'` регистрирует сервис в корневом инжекторе: один экземпляр на всё приложение (singleton), поэтому состояние в `AuthService` общее для всех компонентов. Если сервис нигде не используется, tree-shaking выкинет его из бандла.

## Этап 8. Angular: auth-сервис, interceptor, guard, logout

### Что сделано
- `AuthService`: `login`/`register` (HTTP + сохранение токена), `logout`, сигналы `token`, `email`, `isLoggedIn`.
- `authInterceptor` добавляет `Authorization: Bearer ...`, а при 401 делает logout.
- `authGuard` (только для залогиненных) и `guestGuard` (только для гостей).
- Страницы логина и регистрации на **Reactive Forms** с валидацией (включая проверку совпадения паролей).

### Ключевые концепции

**Где хранится токен.** В `localStorage` (переживает перезагрузку страницы). Вместе с ним хранится `expiresAt`: при старте приложения просроченный токен сразу удаляется.
*Минус localStorage:* при XSS-уязвимости скрипт злоумышленника может прочитать токен. Альтернатива — `HttpOnly` cookie (JS не может её прочитать), но тогда нужна защита от CSRF. Для тестового задания localStorage проще и нагляднее.

**Interceptor** — функция, через которую проходит каждый запрос `HttpClient`:
```ts
request.clone({ setHeaders: { Authorization: `Bearer ${token}` } })
```
`HttpRequest` неизменяемый (immutable), поэтому делаем копию. В `catchError`: если сервер ответил 401 и токен был, значит он истёк или невалиден, и мы делаем logout с редиректом на `/login`.

**Guard** запускается до перехода на маршрут. Возвращает `true` (пустить) или `UrlTree` (перенаправить). Guard — это **UX, а не безопасность**: защищают данные `[Authorize]` и фильтрация по `userId` на сервере. Guard лишь не показывает пустую страницу гостю.

**Observable и `subscribe`.** `http.post()` возвращает Observable — «рецепт» запроса. Запрос уходит только при `subscribe()`. Оператор `tap()` выполняет побочный эффект (сохранить токен), не меняя данные. HTTP-Observable завершается после ответа, поэтому отписываться не нужно.

**Reactive Forms:**
```ts
form = fb.nonNullable.group({
  email: ['', [Validators.required, Validators.email]],
  password: ['', [Validators.required, Validators.minLength(6)]],
}, { validators: passwordsMatchValidator });
```
- `[formGroup]="form"` и `formControlName="email"` связывают шаблон с моделью;
- `form.controls.email.touched && invalid` — показываем ошибку только после того, как пользователь тронул поле;
- `markAllAsTouched()` при отправке невалидной формы показывает все ошибки;
- **валидатор на уровне группы** (`passwordsMatchValidator`) проверяет два поля вместе.
- Клиентская валидация — для UX. Сервер **всегда** валидирует повторно, потому что клиент можно обойти.

### Вопросы и ответы

**1. Что такое HTTP interceptor и зачем он здесь?**
> Это middleware для исходящих HTTP-запросов на клиенте. Здесь он (1) добавляет JWT в заголовок `Authorization` каждого запроса, чтобы не делать это в каждом сервисе вручную; (2) централизованно обрабатывает 401: разлогинивает пользователя, когда токен истёк.

**2. Защищает ли route guard данные? Что будет, если его обойти?**
> Нет. Guard работает в браузере, и его можно обойти (DevTools, прямой вызов API). Он только улучшает UX. Данные защищает сервер: `[Authorize]` вернёт 401 без валидного токена, а фильтрация по `userId` не отдаст чужие данные.

**3. Чем Reactive Forms отличаются от Template-driven forms?**
> В Reactive Forms модель формы (`FormGroup`, `FormControl`, валидаторы) создаётся в TypeScript, а шаблон только привязывается к ней. Это явно, типизировано, удобно для сложной валидации и тестов. В Template-driven forms форма описывается в HTML через `ngModel`; так проще для мелких форм, но логика размазана по шаблону.

## Этап 9. Angular: список задач, пагинация, поиск, фильтры, CRUD

### Что сделано
- `TasksPage` — **container**-компонент: хранит состояние, вызывает сервисы.
- `TaskItem`, `TaskDetails`, `Pagination`, `CategorySidebar` — **presentational**-компоненты: получают данные через `input()` и сообщают о действиях через `output()`.
- Быстрое добавление задачи, переключение «выполнено», панель редактирования, удаление с подтверждением.
- Поиск с **debounce**, фильтр по статусу и категории, пагинация.

### Ключевые концепции

**Container vs presentational** (как «умные» и «глупые» компоненты в React). `TaskItem` ничего не знает про HTTP: он получает `task` и вызывает `toggle.emit(task)`. Решение принимает `TasksPage`. Такие компоненты легко переиспользовать и тестировать.

**Debounce поиска:**
```ts
searchControl.valueChanges.pipe(
  debounceTime(300),        // ждём 300 мс после последнего нажатия
  distinctUntilChanged(),   // не реагируем, если значение не изменилось
  takeUntilDestroyed(),     // автоматическая отписка при уничтожении компонента
).subscribe(() => { page.set(1); loadTasks(); });
```
Без debounce на слово «milk» ушло бы 4 запроса.

**`switchMap` против гонки запросов (race condition).** Проблема, найденная при e2e-тесте: пользователь быстро кликает «Work», потом «Groceries», а ответ для «Work» приходит позже и перезаписывает список. Решение:
```ts
reload$.pipe(switchMap(() => taskService.getTasks(buildQuery())))
```
`switchMap` при новом событии **отменяет предыдущий HTTP-запрос** и подписывается на новый. На экране всегда результат последнего запроса. `catchError` внутри `switchMap` нужен, чтобы ошибка одного запроса не «убила» весь поток.

**Почему после каждого изменения мы перезагружаем список, а не правим массив локально.** Пагинация и фильтры серверные: после добавления, удаления или выполнения задачи меняются и порядок, и `totalCount`, и содержимое страницы. Проще и надёжнее запросить актуальную страницу. Крайний случай: удалили последнюю задачу на странице 3, тогда переходим на последнюю существующую страницу.

**`effect()` в `TaskDetails`** — при выборе другой задачи (меняется `input` `task`) форма заполняется её данными через `form.reset(...)`.

**`[ngValue]` в `<select>`** — сохраняет настоящий тип значения (`number` или `null`). С `[value]` всегда получилась бы строка.

**`$event.stopPropagation()`** — клик по кружку «выполнено» внутри строки не должен открывать панель деталей (событие не всплывает к родителю).

### Вопросы и ответы

**1. Что такое Observable и чем он отличается от Promise?**
> Promise — одно значение в будущем; выполняется сразу при создании; отменить нельзя. Observable — поток из 0..N значений во времени; **ленивый** (ничего не делает до `subscribe`); **отменяемый** (`unsubscribe`, `switchMap` отменяет HTTP-запрос); есть операторы (`map`, `debounceTime`, `switchMap`). `HttpClient` возвращает Observable, который выдаёт одно значение и завершается.

**2. Как реализован поиск и зачем debounce?**
> Поле поиска — `FormControl`, у него есть Observable `valueChanges`. Через `debounceTime(300)` мы ждём, пока пользователь перестанет печатать, `distinctUntilChanged` отсекает повторы, затем сбрасываем страницу на 1 и перезагружаем список. Сам поиск выполняет сервер (`LIKE` в SQL). Debounce снижает нагрузку: один запрос вместо запроса на каждую букву.

**3. Что делает switchMap и какую проблему он решает у вас?**
> `switchMap` превращает каждое событие во внутренний Observable (HTTP-запрос), а при новом событии отписывается от предыдущего, и Angular отменяет незавершённый запрос. Это решает race condition: медленный ответ на старый фильтр не перезапишет результаты нового.

## Этап 10. Angular: категории и UI

### Что сделано
- `CategorySidebar`: «All tasks», список категорий, создание («New list» + Enter), переименование прямо в списке (Enter сохраняет, Esc отменяет), удаление с подтверждением.
- Задача, созданная внутри категории, попадает в неё.
- UI в стиле Microsoft To-Do: синяя шапка с поиском, сайдбар слева, панель деталей справа, просроченные сроки подсвечены красным.
- Адаптивность: на мобильных сайдбар заменяется на `<select>`, панель деталей открывается на весь экран.

### Ключевые концепции

**`viewChild()`** — ссылка на элемент шаблона (`#editInput`), аналог `useRef`. Вместе с `effect()` даёт автофокус на поле переименования, как только оно появилось (HTML-атрибут `autofocus` работает только при загрузке страницы).

**Template reference variable** (`#categorySelect`) — ссылка на DOM-элемент прямо в шаблоне: `categorySelect.value`.

**Ошибки API в UI.** `getErrorMessage()` достаёт текст из ProblemDetails (`detail`) или из ошибок валидации (`errors`) и показывает баннер (например, «Category 'Work' already exists.»).

### Вопросы и ответы

**1. Как родительский компонент узнаёт, что в сайдбаре создали категорию?**
> Сайдбар объявляет `readonly create = output<string>()` и вызывает `this.create.emit(name)`. Родитель подписывается в шаблоне: `(create)="createCategory($event)"`, где `$event` — переданное имя. Родитель вызывает `CategoryService`, затем перезагружает категории. Это однонаправленный поток данных: данные идут вниз через `input`, события вверх через `output`, как props и callbacks в React.

**2. Почему сайдбар не вызывает API сам?**
> Так проще контролировать состояние: после изменения категории нужно обновить и список категорий, и задачи, и выбранный фильтр, а всё это живёт в `TasksPage`. Сайдбар остаётся простым и переиспользуемым компонентом без зависимостей от HTTP.
