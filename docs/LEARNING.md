## Этап 1. Solution, 4 проекта, ссылки, docker-compose

### Что сделано
- Создан solution `server/TodoApp.sln` и 4 проекта:
  - `TodoApp.Api` (шаблон `webapi --use-controllers`): контроллеры, `Program.cs`, конфиг;
  - `TodoApp.Services`, `TodoApp.Interfaces`, `TodoApp.DataAccess` (шаблон `classlib`, обычные библиотеки классов).
- Настроены ссылки между проектами (`ProjectReference` в `.csproj`):
  - `Services → Interfaces`
  - `DataAccess → Interfaces`
  - `Api → Services, DataAccess, Interfaces`
- Из шаблона убран демо-код (WeatherForecast) и пакет OpenAPI. Swagger добавим на этапе 4 осознанно.
- Порт API зафиксирован: `http://localhost:5000` (`Properties/launchSettings.json`).
- `docker-compose.yml` поднимает MS SQL Server 2022 в контейнере.
- `.gitignore` (шаблон `dotnet new gitignore`): исключает `bin/`, `obj/` и прочие артефакты сборки.

### Ключевые концепции

**Solution и проект.** Проект (`.csproj`) — это одна сборка (`.dll`). Solution (`.sln`) — просто «папка», которая группирует проекты для IDE и `dotnet build`. Почему 4 проекта, а не 4 папки: ссылки между проектами проверяет **компилятор**. Если `Services` попробует использовать класс из `DataAccess`, код просто не соберётся. С папками такую границу легко нарушить случайно.

**4-уровневая архитектура:**
| Уровень | Что делает | Аналогия |
|---|---|---|
| Controllers (`Api`) | принимает HTTP-запрос, валидирует, вызывает сервис, возвращает HTTP-ответ | официант |
| Services | бизнес-логика: правила, проверки, «можно ли это сделать» | повар |
| Interfaces | контракты: «что умеет» каждый слой, без реализации | меню / договор |
| Data Access | работа с БД через EF Core | кладовая |

**Почему сущности лежат в `Interfaces`, а не в `DataAccess`.** Интерфейс репозитория возвращает сущность: `Task<TodoItem?> GetByIdAsync(int id)`. Если бы сущности лежали в `DataAccess`, то `Interfaces` ссылался бы на `DataAccess` (за сущностями), а `DataAccess` на `Interfaces` (чтобы реализовать интерфейс). Получился бы **цикл**, и .NET запрещает циклические ссылки между проектами. Поэтому сущности (простые классы без логики EF) лежат в центральном проекте.

**Dependency Inversion Principle (D в SOLID).** Модули верхнего уровня (Services) не зависят от модулей нижнего уровня (DataAccess). Оба зависят от **абстракций** (интерфейсов в `Interfaces`). Плюсы:
- `Services` не знает про EF Core/SQL, поэтому БД можно заменить, не трогая бизнес-логику;
- в unit-тестах вместо настоящего репозитория можно подставить мок.

**Composition root.** Это единственное место, где «собираются» конкретные реализации: `Program.cs` в `Api`. Поэтому `Api` ссылается и на `Services`, и на `DataAccess`: там мы скажем DI-контейнеру «когда кто-то просит `ITaskRepository`, дай `TaskRepository`».

**Docker / docker-compose.**
- *Образ (image)* — шаблон (SQL Server 2022 от Microsoft). *Контейнер* — запущенный экземпляр образа.
- `docker-compose.yml` описывает контейнеры декларативно, и одна команда `docker compose up -d` поднимает БД. Не нужно ставить SQL Server на машину, у всех разработчиков одинаковая версия.
- `ports: "1433:1433"` — порт хоста : порт контейнера. API подключается к `localhost:1433`.
- `volumes` — данные БД хранятся вне контейнера, поэтому переживают `docker compose down`. `down -v` удаляет и их.
- `healthcheck` — Docker каждые 10 сек выполняет `SELECT 1`, чтобы понять, готова ли БД принимать запросы (старт SQL Server занимает ~10–20 сек).
- Пароль SA лежит в compose-файле открыто. Это допустимо **только для локальной разработки**. В проде секреты хранят в переменных окружения / секрет-хранилищах (Azure Key Vault и т.п.).
